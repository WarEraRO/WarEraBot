# WarEra API skill

This bot (discord.py, async, aiohttp) is built on the public WarEra API. This skill is both the API reference and the **decision procedure** for any new WarEra-related work.

The API is a **tRPC** server at `https://api2.warera.io/trpc/<router>.<procedure>`. Every known procedure is a **read-only query**, so the public API has no write or action endpoints. The skill covers **96 live procedures** (verified 2026-10-03, re-checked 2026-10-26 after the game's v0.27 patch, 2026-10-28 after v0.27.1 and 2026-11-02 after v0.27.4):
- **37** from the official spec (version **0.17.4-beta**; v0.27 added `poll.*` and removed `worker.*` and `workOffer.*`).
- **59 more (🧭)** that the official spec omits (10 were added to the explorer by 2026-10-28, among them the manager job market, patch notes and per-employee work, and the ten `employee.*` / `employeeEvent.*` queries by 2026-11-02). They're documented by the community explorer https://warera.realmarijn.nl/api-explorer, and each was verified live. They include alliances, diplomacy, wars, parties, elections, donations, MU member stats, tournament listings, work stats and construction. The explorer still lists some v0.27-removed procedures (`workOffer.getWageStats`, `work.getStatsByWorker*`); the index marks them ❌.

> **WarEra v0.27 (2026-10-25)** replaced the job market with NPC employees and player managers, removed the Entrepreneurship skill (Leadership is new), party ethics, deposits and country specialization, and added government types (`country.govType`). Treat older facts about jobs, wages, skills or production bonuses as stale. The manager listing and pay range (`managerOffer.getManyPaginated`, `getWageStats`) are 🧭; the per-company manager contract is 🕵️ client-only, and the ten **employee** queries (`employee.*`, `employeeEvent.*`, announced as API-token endpoints on 2026-10-28) are 🧭 since the explorer added them by 2026-11-02. v0.27.1 (2026-10-27) divided manager wages by 10.

## Mandatory workflow (do this before implementing anything WarEra-related)

**Step 1: Translate the request into API needs.** Write down concretely: *retrieve one entity by ID? look up by name? list or paginate a collection? current state (live battle, prices)? history (events, transactions)? game constants?* Note which IDs you already have. Most procedures need Mongo ObjectIds (24 hex chars), not names.

**Step 2: Search the endpoint index.** Open [references/endpoints-index.md](references/endpoints-index.md) and search by *intent*, not by name. Read the `Use when` lines. Check [references/game-config.md](references/game-config.md) before hardcoding **any** game number (costs, percentages, skill tables, item stats, upkeep, battle rules).

**Step 3: Check existing project usage.** Open [references/project-usage.md](references/project-usage.md). If a `warera` client method already wraps the procedure (`tools/agent-cli proc <procedure>`), call it. If a procedure isn't wrapped yet, add a method **to the matching class in `warera/endpoints/`** that follows the conventions below. Don't put raw HTTP calls in a cog.

**Step 4: Compare alternatives**, preferring them in this order:
1. one purpose-built endpoint;
2. an existing project helper around that endpoint;
3. a small combination of endpoints;
4. local derivation from raw API data;
5. custom or duplicated logic (hardcoded tables, scraping, N+1 fan-out).

If you pick anything below #1, say why in one sentence. If the project currently uses a worse path for the same data, **tell the user before implementing** (see [references/api-opportunities.md](references/api-opportunities.md)).

**Step 5: Implement consistently.** Follow the project conventions below. Don't create a new client or session.

> **The key question.** Whenever a solution needs more than one API call or any non-trivial local computation, stop and ask: *"Does the WarEra API already expose this result more directly?"* Check the index and `gameConfig` before continuing. This is the main reason the skill exists.

## API rules

- **Don't invent** procedures, input fields, response fields, enum values or auth requirements. If something isn't in the spec or observed, say it's unknown.
- The documentation labels every fact with its source. Keep those labels when you add facts:
  - **[spec]**: from the official OpenAPI document (inputs, enums, descriptions).
  - **[explorer]**: from the community explorer (warera.realmarijn.nl). Third-party, and some of its params are silently ignored live, so prefer **[observed]** facts over it.
  - **[observed]**: seen in live responses while building this skill (2026-10-03). The spec has *no response schemas*, so every response shape is observed.
  - **[project]**: inferred from how this codebase uses the field.
  - **[assumption]**: unverified inference. Verify it before relying on it.
- **Freshness.** Live docs win over this skill. When exact params or response fields matter and you have network access, verify them against `https://api2.warera.io/openapi.json`, the explorer, or one live call (`curl "https://api2.warera.io/trpc/<proc>?input=<urlencoded json>"`). For ad-hoc checks use `python -I .claude/skills/warera-api/scripts/probe.py <proc> ['<json input>'] [--anon]` (bot key from `.env`, never printed; GET only; refuses names without a `get`/`search` prefix; ~1 call/s). It prints a `###` status line, then the JSON **cut to 1500 characters**: pass `--chars 200000` and parse the line starting with `{` when you need fields deep in a big object such as `user.getUserById` or `gameConfig.getGameConfig`. If you write your own Python check, send a `User-Agent` header: plain `urllib.request.urlopen` gets **403** while curl and aiohttp succeed **[observed 2026-10-06]**. If the live API differs, update the skill or flag the difference to the user. Run `python .claude/skills/warera-api/scripts/refresh_spec.py --check` to diff **both** the official spec and the explorer against their snapshots. It has no `--help`: any run without `--check` (including `--help`) **rewrites** the snapshots and the generated inputs file.
- **After a WarEra game patch** (the admin pins the patch notes; read them with 🕵️ `article.getPinnedArticles`): `refresh_spec.py --check` alone isn't enough, because it only sees the official spec and the explorer. For v0.27 most of the changes were client-only. Do all of these:
  1. Run `refresh_spec.py --check`. Live-probe every procedure it reports REMOVED, because the explorer lags: it still listed the dead `workOffer.getWageStats` after the patch.
  2. Re-run the client discovery (client-discovered.md → "Repeating the discovery"). Diff against everything the docs name, including the `- **router**: a, b` lists in client-discovered.md. Probe the new queries with the bot key, about 1/s, queries only. **Also re-probe the queries recorded as 403 or "not probed"** (client-discovered.md E/F): access can open with no new procedure and no spec or explorer change. `employee.*` went from 403 to readable between 2026-10-26 and 2026-10-28; a community post announced it first, and the v0.27.2 patch notes gave it a single line. Patch notes are a weak signal for API changes, so probe anyway. Some procedures (`employee.getCompanyEmployees`, `getCompanyEstimate`) aren't in the client bundle at all, so announcements are the only way to learn about them.
  3. Grep `cogs/` and `utils/` for each removed procedure, removed response field and removed skill or config key.
  4. Run the `warera-config` drift check (`check_config.py`) for changed constants.
  5. Diff **response shapes**: `python -I .claude/skills/warera-api/scripts/check_shapes.py --out <scratchpad>/shapes.json` probes every indexed query once (~100 calls, ~2 min) and lists live keys no doc mentions, plus doc-sample keys missing live. A key missing from one sample is often just optional (`buffs`, `party.treasurer`): confirm a removal over 20+ objects (tRPC batch) before documenting it. On 2026-11-02 this found `user.company`, region `deposit` and employee `region` removed with no spec, explorer or patch-note signal.
  Removed procedures answer **404 `No procedure found on path`**, and the client methods turn that into `None` (logged as an error, `ProcedureNotFoundError`). A feature built on one then silently shows its "unavailable" message, so nothing crashes or alerts you.
- **Stability tiers:** official spec > 🧭 explorer-documented > 🕵️ game-client internal (client-discovered.md). Pick the highest tier that does the job.
- **Never call mutations.** This bot is read-only. The game's internal API includes hundreds of action procedures (hit, trade, vote, moderation). Don't invoke them, even to "test".
- **Terms of Use (reported, unverified).** A player's summary of the Terms effective 2026-09-28 (in-game article `6aca745113d6372b785457bc`) says the public-API rules forbid scraping, getting around rate limits and **using non-public endpoints**. That could cover the 🕵️ client-only procedures. Nobody has read the official Terms for this skill yet. Before building a new feature on a 🕵️ procedure, tell the user about this and suggest checking the official Terms; prefer an official or 🧭 procedure when one does the job.
- **Silent ignoring.** The server ignores unknown or unsupported input keys. A 200 response doesn't prove a filter worked, so check that the results actually reflect the filter before relying on a new param.
- **Procedures outside the official spec** (🧭 in the index, plus `gameStat.getEquipmentAvgByCode` used in `cogs/commands/damage.py`, and `tournament.getById` + `tournamentTeam.getById` used via `warera.tournaments` in `battle-order_monitor.py`) are real but unofficial. Prefer an official procedure when one does the job equally well. When you use a 🧭 one, say so in a code comment and to the user.

## Project conventions (the `warera/` client package)

All WarEra API access goes through one `WarEraClient` (package `warera/`, documented in `warera/README.md`). The bot's instance is `from utils.api import warera`; `run.py` closes it with `await warera.close()`. Never build URLs, encode `input`, unwrap `result.data` or open a session in a cog.

- **Calls:** high-level methods per area: `warera.users`, `countries`, `regions`, `mus`, `battles`, `tournaments`, `contracts`, `companies`, `market`, `game` (for example `await warera.users.get_many(ids)`, `await warera.battles.get_active()`). Find the method for a procedure with `tools/agent-cli proc <procedure>`.
- **Return contract:** a method returns `result.data`, or **None** when the call failed or the shape is wrong. A batch method returns `{key: data}` and **leaves out** keys that failed or came back empty. Methods never raise: API errors are logged (an expected 404 at debug only), and an unexpected crash in a method's parsing is logged with its traceback. Callers treat `None` as failure and show a friendly ephemeral message.
- **Errors:** `warera.call(procedure, input)` raises the `WarEraAPIError` hierarchy (`ValidationError` 400, `AuthenticationError` 401/403, `NotFoundError` 404 → `ProcedureNotFoundError` for a removed procedure, `RateLimitError`, `ServerError`, `NetworkError`, `InvalidResponseError`). `warera.call_many` / `warera.batch` return those errors in place of failed items. Use these only when a feature must tell "not found" from "failed".
- **Transport:** GET only (tRPC serves mutations only over POST). `X-API-Key` is sent per request, never as a session default. 429 (honouring `Retry-After`), 5xx and network errors are retried with jittered exponential backoff (5 attempts, capped at 60 s); other 4xx are not. Each attempt times out after 60 s. At most 10 requests are in flight at once, and new requests wait while `ratelimit-remaining` is 0.
- **Batching:** a tRPC batch of up to 100 calls costs **1** rate-limit unit **[observed 2026-10-09]**. For fan-out of one procedure (one call per member/ID), use the `*_many` methods or `warera.call_many(procedure, inputs)`: identical inputs are sent once, chunks hold 50 calls (or less URL), and results stay aligned. Calls started together (`asyncio.gather`) are also **coalesced** into one batched request automatically, so per-cog semaphores are rarely needed. A 207 slot error affects only that item.
- **Caching:** identical in-flight calls always share one request. Only procedures in `DEFAULT_CACHE_TTLS` are cached: today `gameConfig.getGameConfig`, for 1 h, serving the expired copy when a refresh fails. Don't mutate cached objects. Live data is not cached centrally; cogs keep derived caches (country-name maps, MU names) where staleness is fine.
- **Pagination:** `Endpoint._collect` (cursor loop; `partial=True` keeps the pages read before a failure) and `_collect_since` (newest-first listings cut at a `createdAt`). Don't copy-paste cursor loops.
- **New procedure:** add a method to the matching class in `warera/endpoints/` with `@guarded()` and the `Endpoint` helpers (`_get`, `_get_keyed`, `_collect`). Document 🧭/🕵️ status in a comment, and add a test in `tests/test_warera_client.py` (see warera/README.md → Adding an endpoint). Run the tests with `python -m unittest discover -s tests` (no `-t .`: `tests/` isn't a package, so discovery then fails with "Start directory is not importable"). They use a local `aiohttp.web` fake tRPC server and never touch the live API.
- **Verified live (2026-11-02, bot key):** four concurrent calls, two of them no-input procedures sent with their batch index left out, came back in one request with correct data. An unknown `mu.getById` raised `NotFoundError` (404 `NOT_FOUND`), and a removed procedure raised `ProcedureNotFoundError`. For a quick live check, call `utils.api.warera` from `env/Scripts/python.exe` and print `warera.transport.request_count`; read only, a handful of calls.
- **IDs:** API objects use `_id`. Some cogs defensively read `_id or id`.

## Quick answers

- **Username → user:** there's no lookup by username. Use `search.searchAnything` to get `userIds`, then `user.getUserLite` for each and match `username` exactly. This is already wrapped as `warera.users.find_by_name()`, and the id is cached in `warera.users.username_ids`. For **many names** (every Discord member) use `warera.users.find_many_by_name(names)` (full users, batched) or `warera.users.ids_by_name(names)` (IDs only; cached names cost no request). Search returns at most 5 fuzzy matches, so an unquoted short name ("Tert", "Ptm") can miss its own player; the helpers send the name **quoted** (`"Tert"`, exact phrase) first and fall back to plain. Never build a raw `searchAnything` username lookup without that quoting (see domain-users.md). When a Discord member is linked in the DB (`get_api_ids_by_discord_id`), prefer the id over any name search.
- **Country citizens are not a full directory:** `user.getUsersByCountry` for Romania returned only 320 ids and missed a Romanian citizen **[observed 2026-10-24]**. Don't use it to resolve names or to prove someone isn't a citizen. For **every citizen of a country** in one request, filter `ranking.getRanking` `userWealth` (or `userLevel`) on `country`: those rankings list every player, zero wealth included (14,697 items each, 350 Romanians) **[observed 2026-11-03]**. Their `country` is a snapshot, so re-check `user.country` on the loaded users.
- **A player's weekly bounty:** there's no weekly bounty ranking (`userBounty` is all-time). Per ended battle, `battleRanking` `money`/`user`/`merged` lists everyone paid (bounty + contract pay), and the loot summary splits it (`totalMoneyFromBounty`); batch pairs across battles with `warera.battles.get_loot_summaries_many`. A player's **monthly damage** the same way: sum `battleRanking` `damage`/`user`/`merged` over the month's ended battles (no monthly user ranking exists). Worked example: `cogs/tasks/gov_rankings.py` (domain-battles-military.md → `battleRanking.getRanking`).
- **Which configured MU is each player in:** read `members` (user IDs) from `mu.getById`, batched over the configured MUs with `warera.mus.get_many`. Don't fetch each user for `user.mu`.
- **Country by name:** call `country.getAllCountries` once and match `name`. Cache the result; it's ~180 items.
- **A single battle by ID:** use `battle.getById` (or `battle.getLiveBattleData` for live score). Don't list all active battles and filter.
- **Prices:** `itemTrading.getPrices` takes **no input** and returns `{itemCode: price}` for every tradable item. Use `tradingOrder.getTopOrders` for the order book.
- **Constants** (upkeep %, skill costs and values, item stats, battle bonuses): use `gameConfig.getGameConfig`.
- **Player wealth breakdown** (money, items, equipments, weapons, companies): `user.getUserById` → `stats.wealth`, batched with `warera.users.get_full_many`. It's a superset of `getUserLite` for buffs/skills/dates **[observed 2026-10-14]**, so switching costs no extra request. Fight wealth (no companies): `utils/computational.fight_wealth`.
- **Who took an MU's mercenary contract, and each member's damage and money:** per-contract data (`mercenaryContract.*`) is 403 for API keys. Use the won auction's `currentWinnerUser` (the taker), then `battleLootSummary.getByBattleAndUser` per member for `totalMoneyFromContract` (pooled per battle). See domain-battles-military.md → Won contracts.
- **Who did damage in a battle, round or war:** use `battleRanking.getRanking`. Don't sum `round.getLastHits`.
- **Tournament battles** (`battle.type == "tournament"`): they have no region or side `country`. Use `tournament.getById {tournamentId}`: its `type` is `country` or `mu`. Then use `tournamentTeam.getById {tournamentTeamId}` per side: `countries[]` is the coalition, `mus[]` the MU. Both are undocumented.
- **Country flag:** `country.code` is the ISO 3166 alpha-2 code, so the Discord flag is `:flag_<code>:`. `utils/common.py:COUNTRY_FLAGS` holds all 180 countries. Exceptions: United Kingdom's code is `uk` but the flag is `gb`; United Korea (`kp`) is mapped to `:flag_kr:` by project choice.
- **Auth required (401 without key):** `transaction.getPaginatedTransactions`, 🧭 `company.getRecommendedRegionIdsByItemCode`, and 🧭 `work.getStats*` (×4; per the explorer these also need Premium).
- **MU members' weekly/monthly damage and help:** 🧭 `muMember.getByMu {muId}`, one call for all members.
- **Donations:** 🧭 `donation.getManyPaginated` gives **lifetime** per-donor totals to a country, MU or party (no key needed), and `donation.getTotalDonations` gives the sum. **Weekly** figures still need `transaction.getPaginatedTransactions` 🔑.
- **Romania's friendly countries (pacts + alliance):** the `country.getAllCountries` item already has `defensivePacts[]` (same ids as `countryDiplomacy`) and `allianceId`; add the members of 🧭 `alliance.getById` (`warera.countries.get_alliance`, skip `suspended`). Two requests, no per-country fetch **[observed 2026-10-25]**. See `cogs/tasks/bounty_alerts._load_friendly_countries`.
- **Sworn enemy and defensive pacts with damage dealt:** 🧭 `countryDiplomacy.getByCountry`. **War score:** 🧭 `war.getById`.
- **Elections and results:** 🧭 `election.getElections {countryId|partyId}` (always pass one; otherwise you get a 500, which the project retries). Read the tally from the `votes` map.
- **Jobs since v0.27 (2026-10-25):** the job market and every `workOffer.*` / `worker.*` procedure are **gone (404)**. Players work in their own companies (self-work) or as **managers**: 🕵️ `managerOffer.getManyPaginated` lists manager jobs and `managerOffer.getWageStats` the allowed pay range. The value of 1 production point is 🧭 `gameStat.getPpMoneyValue` (no input).
- **Employees (NPC workforce) of any company:** 🧭🔑 `employee.getCompanyRoster {companyId}` gives every employee with estimates plus the company's hourly production, wage and manager cost in one call; `getCompanyEstimate` gives only the totals. One employee: `employee.getById`; their hourly work: `work.getLastByEmployee`. The `getMy*` and `employeeEvent.getMine` / `getPendingCount` procedures describe the **API key's owner**, never the Discord user. Details: domain-economy.md → Employees.
- **Value of production per good:** 🕵️ `gameStat.getPpMoneyValueByItem` (no input, no key) gives money per production point for each tradable good; the global value is `gameStat.getPpMoneyValue`.
- **Donations to a country:** `transaction.getPaginatedTransactions {countryId, transactionType:"donation"}` 🔑 returns donations **to** that country (donor in `buyerId`) **[observed 2026-11-02]**.
- **Patch notes / game version:** the admin pins them; 🧭 `article.getPinnedArticles`.
- **Tournaments:** 🧭 `tournament.getLastTournament`, `tournament.getManyPaginated`, and `tournamentTeam.getByTournamentId` (all teams in one call).
- **"Get the data from this community website":** WarEra community tools on GitHub Pages or Netlify are usually client-only apps (empty `<div id="root">`) that call `api2.warera.io` from the browser. They have no data of their own and no server to query. Two were checked 2026-10-25: War Era Coach and economic-build-warera.netlify.app. To read one:
  1. `curl` its `index.html` and the `/assets/index-*.js` bundle into an empty scratchpad folder.
  2. Grep the bundle for `trpc/` and the formula (with Python, because the bundle isn't cp1252-safe).
  3. Check GitHub for a source repo. Many have **no license**, so rewrite the logic rather than copying it.

  Then reproduce the procedures it calls with the bot's own helpers. The game-expert skill's `source-map.md` lists the models found so far.
- **A player's job, party, MU and daily reward:** `user.company` is **gone** since the job market ended (0 of 24 users had it on 2026-11-02), so don't treat its absence as "unemployed"; `party` / `mu` are missing when the player has none. Read the daily reward from `dates.lastDailyCalendarClaimedAt`; `lastDailyRewardClaimedAt` is stale. Mission progress and inventory are not readable (see domain-users.md).
- **A player's damage on one day / since a moment:** snapshot `user.rankings.userDamages.value` (all-time, updated within minutes) and subtract; batched with `warera.users.get_full_many`. See domain-users.md.
- **How many of a player's companies are disabled:** there is no flag; disabled = owned − `skills.companies.value` (see domain-economy.md → `company.getById`).
- **Missions a player completed today:** not exposed (`mission.*` queries are 403 for API keys). `user.getUserById` → `missions` gives the **lifetime** `claimedCount` and `claimedAt.daily` (claimed dailies today if after `previousDayAt`). An exact daily count needs a `claimedCount` snapshot at 00:00 UTC (see domain-users.md).
